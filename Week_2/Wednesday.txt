### Data storage and accompanying factors

#### Pipelines

**ETL - Extract Transform Load**
- **E** - Take it from a data source/ collection system
	- Machinery sensors
	- Excel files
	- File types : .csv (separated by commas), .JSON (key value pairs), .txt (unseparated text) 
- **T** - Manipulate if necessary
	- Clean the data
	- Generating new metric
	- Converting file or bringing files together
	- SQL
- **L** - Load into storage
	- Putting the cleaned and ready data into organised storage for use

For different storage systems (data lakes for example)

**ELT - Extract Load Transform Analytics**
- E - Take from data source
- L - Load into structured data file
- T - Manipulate for use
- A - Understanding what the data is telling us

Organised collection of data giant filing system
- **Store** 
- **Retrieve**

#### Relational Data Processing (SQL)
Managing business data for purpose

**OLTP - Online Transaction Processing**
- Online transaction processing
- Database transactions
	- Payments received
	- Orders taken
	- Bookings
	- Inventory movement
- High degree of normalisation
	- Managing the dataset
	- Low repetition
	- Organising efficiently
- Heavy write low read
	- Writing to a lot
		- Adding new records 
		- Correcting records
	- Reading not a lot
		- Reports
		- Queries
- **Must adhere to *ACID* (Database remains valid in error, valid state every time)**
	- **Atomicity**
		- Single unit
		- If part fails all fails
	- **Consistency**
		- Each transaction => valid database state
	- **Isolation**
		- Concurrent read/write executions should produce the same result as sequential executions
	- **Durability**
		- Transactions must remain committed in the event of system failure


**OLAP - Online Analytic Processing**
- Extract business intelligence from ***OLTP***
- Adds a layer of abstraction and aggregation
	- Semantic data models describe meaning if data elements
	- Data integration from multiple sources aggregated together over multiple dim
- Heavy read low write

#### Kimball Dimensional Modelling techniques

4 key steps of dimensional design process 
- **Select business process**
	- *Operational activities performed by the organization*
		- Taking orders
		- Processing an insurance claim
		- Registering students for a class
	- Capture and generate performance metrics that go into the fact table
	- Targeting a single process allows for the rest of the steps to be defined
	- Corresponds toa  row in the enterprise data warehouse bus matrix
- **Declare the grain**
	- Grain establishes what a single fact table row represents
	- Must be chosen next because all information must be consistent with the grain
		- Ensures ***Uniformity***
	- Atomic grain - lowest level at which data is captured by a process
		- Start focussed on this because its more solid for queries
	- More than one grain => more than one fact table
- **Identify the dimensions**
	- Key links to the fact table, cleanly connects numerical measurements to descriptions
	- Who, what, where, when, why, and how? about a process
	- Using grain all possible dimensions can be identified
- **Identify the facts**
	- Facts are the measurements that result from a process
	- A single fact row has a one-to-one relationship with the measurement event according to the grain of the fact table
	-  Corresponds to a physical event

**Star Schemas**
- Dimensional structures deployed in a relational database management system. 
- Fact table -> associated dimension tables (primary/ foreign key relationships)
- **OLAP** cube is a dimensional structure implemented in multidimensional database (or relational star schema)
- More advanced than SQL (e.g. XLMA)
- Final step in deployment of a dimensional DW/BI system

#### Fact table deeper dive
Numeric measures are one of the following
- Additive - summed across dimensions
- Semi-additive - summed across some dimensions but not all
- Non-additive - (ratios) cannot be summed anywhere

NULL entries behave gracefully
- All aggregate functions do the 'right thing'
NULL's avoided in the fact tables foreign keys section

Conformed facts are facts that have to be identical if they share similarities in the technical definitions

#### Dimension Table deeper dive
**Structure** is as follows
- Single primary key column, embedded as a foregin key in any associated fgact tabel
- Wide and flat denormalized tables with many text attributes
- Anonymous keys for every dimension, i.e. dimension surrogate keys
- Natural keys (ID numbers) are independent of the system, business side

**Drilling down** - most fundamental way data is analysed 
- Adding a row header to an existing query
- GROUP BY in SQL
##### Conformed Dimensions
- Dimension tables conform if a different Dimension table has the same attribute column name and contents
- **Drilling across** - comparing fact tables with identical row headers
- **Enterprise Data Warehouse Bus architecture** - incremental approach to building the enterprise DW/BI system
	- Breaks up the planning stage into manageable pieces
	- Provides architectural framework in an ***Agile*** way
- Uses the **Enterprise Data Warehouse Bus Matrix** for design and communicating the architecture
